## What this project is about

General-purpose CLI/agent orchestration work in `/private/tmp` — no persistent codebase. Sessions are exploratory, multi-agent, and decision-heavy, with recurring focus on warden/background-execution patterns and owner-facing decision UIs.

## Things to do (or keep doing)

- Always identify the widest plausible audience before finalizing any artifact (GitHub comments reach teammates; HTML reaches non-engineers); verify attribution, register, and format for that audience before sending.
- When verifying a UI, read the specific element the complaint targets by screenshot/rendered pixels — not an a11y snapshot, not a nearby panel, not a DOM dump.
- Apply fixes directly within your own scope; prefer action over IPC coordination with peer agents when the fix is yours to make.
- Label gate entries (`blocked_on: USER:`) only when the owner can act on them *today* — prerequisites belong to the blocking work, not the owner queue.

## Things to avoid

- Don't halt mid-task without a genuine blocker only the owner can resolve; when the user says "keep going" after a pause, the prior stop was unjustified — don't re-raise the same soft blocker.
- Don't claim a surface was verified via an a11y snapshot or skill name listed in a SKILL.md; only a rendered screenshot read top-to-bottom constitutes visual verification.
- Never use literary or narrative phrasing in technical output ("The build chase ended…"); zero em-dashes, zero bold-spam, no register drift.
- Don't build or direct owners to a decision UI without first exercising it (curl or screenshot) to confirm it is functional.

## Open questions / known gaps

- Warden/background-execution agents repeatedly idle or halt despite standing go-aheads; frontloading blockers hasn't fixed this — the threshold calibration for autonomous continuation remains unresolved.
- Decision UIs consistently cost the owner more effort than direct chat; the right granularity for wizard vs. inline vs. prose reply has not stabilized.
