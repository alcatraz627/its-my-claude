# Codex adapter

Codex runs on the same disk as `~/.claude/`, so it can read the config directly.
The adapter is therefore a **router**, not a copy. Nothing is duplicated into
Codex's world except one preamble and one index.

## The chain

```
adapters/codex/preamble.md   (hand-authored, the only file a human edits)
        +
rules/00-index.md            (generated by scripts/rules-index.sh)
        |
        v  scripts/export-agents-md.sh
        |
$CODEX_HOME/AGENTS.md        (generated, loaded by Codex every turn)
```

Plus one hook, registered independently:

```
adapters/codex/hooks/guard-destructive.sh  <-  $CODEX_HOME/hooks.json
```

## Why the index and not the rules

`rules/*.md` is about 176k chars of standing instruction. Claude Code autoloads
it under a subscription, where the marginal cost of a token is already paid.
Codex bills per token and re-sends `AGENTS.md` on every turn, so inlining the
corpus would put roughly 44k tokens on every Codex turn forever.

`rules/00-index.md` already exists as the progressive-disclosure layer: one line
per rule, about 12k chars. It ships. Codex reads full rules from
`~/.claude/rules/` on demand. The generator enforces a byte cap because Codex
**truncates** an oversized instruction file rather than erroring, which would
silently drop the tail and leave a router that looks installed and is not.

## The invocation that works

```bash
codex exec --sandbox workspace-write \
  --add-dir "$HOME/.claude/checkpoints" \
  -c sandbox_workspace_write.network_access=true \
  "<task>"
```

Each flag buys one thing, verified 2026-08-15:

- `--sandbox workspace-write` lets it edit the repo. The default is `read-only`,
  which is the right default and the wrong mode for doing work.
- `--add-dir "$HOME/.claude/checkpoints"` makes `checkpoint-register.sh` succeed
  **deterministically**. Without it registration is flaky: two runs with
  identical flags, one registered and one did not, and project trust did not
  explain the difference. With it, it works every time.
- `network_access=true` lets the IPC announcement through. Without it the send
  usually fails to connect. This grants full outbound egress, so skip it when the
  handback alone is enough.

Never `--dangerously-bypass-approvals-and-sandbox`. The sandbox is the
enforcement layer here, and that flag is the one thing that removes it.

## Skills port, natively

Codex has its own skills surface at `$CODEX_HOME/skills/<name>/SKILL.md`, with
the same shape as Claude Code's: YAML frontmatter carrying `name` and
`description`, optional `agents/`, `scripts/`, `references/`, `assets/`
subdirectories. Six system skills ship in `skills/.system/` (`review-agent`,
`skill-creator`, `skill-installer`, `plugin-creator`, `imagegen`,
`openai-docs`). User skills go directly in `skills/`, beside `.system/`.

`skills/core-dump/SKILL.md` is the first one, and it is model-invoked off its
`description` exactly like a Claude skill: a prompt saying "use the core-dump
skill" runs it, and so does the owner saying "checkpoint this".

**Skills are the right home for procedures; the preamble is for standing
constraints.** The preamble is re-sent every turn and is charged every turn, so
anything conditional belongs in a skill that loads only when relevant. The
core-dump procedure lives in both today, which is deliberate: the preamble copy
is the fallback if skill discovery ever fails, and it is short. If a third copy
appears, collapse to the skill and link.

## The three layers, and how far each ports

**Prose ports cleanly.** `rules/`, `conventions/`, `GLOSSARY.md`,
`mistake-patterns.md`. No transformation needed, only an address and a read
protocol. `GLOSSARY.md` matters more than it looks: this owner's task phrasing
uses *maximalist*, *surgical*, *one-shotting*, and *efficacy* as terms of art,
and a foreign agent guessing at them produces the wrong shape of work.

**Skills port partially.** A `SKILL.md` body reads fine anywhere. The frontmatter
does not: `allowed-tools` becomes sandbox policy, `user-invocable` and
`argument-hint` are Claude Code UI, and `context: fork` has no equivalent. Any
skill whose value comes from forking (`/bloop` validator dispatch, `/magi`
voters) must not be ported. A `/magi` with five voters in one context is a
checklist, not `/magi`.

**Hooks port further than expected.** Codex 0.147 carries a hook system with the
same wire contract as Claude Code's, verified against the binary's embedded JSON
schema: `decision: approve|block` plus `hookSpecificOutput.permissionDecision:
allow|deny|ask`, over input fields `tool_name`, `tool_input`, `session_id`,
`transcript_path`. Its event roster is `pre_tool_use`, `post_tool_use`,
`permission_request`, `pre_compact`, `post_compact`, `session_start`,
`session_end`, `stop`, `subagent_start`, `subagent_stop`, `user_prompt_submit`.
That is 11 of this config's 13 lanes; only `FileChanged` and `Notification` have
no counterpart.

So the enforcement layer is portable in principle. The adapter deliberately ports
**one** hook anyway, on cost/benefit grounds rather than capability: of 40
PreToolUse registrations here, nearly all tune a teammate (ripgrep preference,
comment hygiene, prose quality) and a contractor's output is reviewed anyway.
Three verbs are different because review happens after the damage: `rm`, git
history/remote mutation, and `gh` writes. Those are what
`guard-destructive.sh` blocks.

## Sync

**Manual, deliberately.** `$CODEX_HOME/AGENTS.md` is regenerated by running
`bash ~/.claude/scripts/export-agents-md.sh`. Nothing watches, nothing schedules
it, and no hook fires it.

Re-run it after either input changes: editing
`adapters/codex/preamble.md`, or adding/renaming/removing a rule (which changes
`rules/00-index.md` after `rules-index.sh` runs). If you forget, Codex runs on a
stale menu and may read a rule file that no longer exists, or miss one that does.
That degrades gracefully: a missing rule is a failed read, not a wrong action.

Automating this is a candidate, not a plan. A PostToolUse hook on writes to
`rules/` would keep it current, but it would be unprompted automation and the
staleness cost is low, so it stays manual until Codex is used often enough to
justify it.

## Known blindness

Codex sessions do not write to `atone/events.jsonl`, so a mistake made by Codex
never enters `mistake-patterns.md` and the monthly mistake curve becomes a
partial read of the agent surface rather than a complete one. This is by design.
That corpus is calibrated to this owner and to Claude, it graduates into rules
and hooks, and feeding a different model's failure modes in would mis-tune the
thing that steers Claude. The blindness is the price and it is the right trade.
Do not build a fix without an explicit decision to widen the corpus.

The same reasoning excludes `memory/`, `runtime-notes.md`, and the dream lanes.
Codex reads; it does not write to institutional memory. Its output goes in
`_codex-handback.claude.md` and the owner decides what graduates.

## Registration: UNSOLVED as of 2026-08-14

`$CODEX_HOME/hooks.json` exists and is shaped as below, but **it does not fire**.
Verified by swapping in a canary hook that denies a unique string, then running
`codex exec` with that string: the command succeeded at exit 0. Adding
`--dangerously-bypass-hook-trust` changed nothing, which rules out the trust gate.

```json
{"version":1,"hooks":{"pre_tool_use":[{"type":"command","command":"<abs path>","enabled":true,"timeout_ms":5000}]}}
```

### The schema, and how the failure hides

The top level takes **only** `description` and `hooks`. A `version` key makes
Codex reject the entire file:

```
warning: failed to parse hooks config ~/.codex/hooks.json:
  unknown field `version`, expected `description` or `hooks` at line 2 column 11
```

That warning is the only signal, it scrolls past in normal output, and `codex
doctor` says nothing about hooks at all. So a malformed hooks file presents
exactly like a correctly-registered hook that never matches. Anyone debugging
this should first confirm the file parses, by watching for the absence of that
warning, before testing anything else.

### Ruled out (2026-08-14, all against a config that parses cleanly)

- **Hook trust.** `--dangerously-bypass-hook-trust` prints its warning and
  changes nothing.
- **The `plugin_hooks` feature flag.** `--enable plugin_hooks` changes nothing.
- **Flat vs matcher shape.** Both `pre_tool_use: [{type, command}]` and
  `pre_tool_use: [{matcher, hooks: [{type, command}]}]` fail to fire.

An earlier round of these tests was worthless because the file was not parsing;
re-run any hypothesis that was tested before the `version` key was removed.

### Remaining lead

The binary carries `"hooks": "./hooks.json"` inside what reads as a **plugin
manifest**, plus `hooks/hooks.json` and `hooks.managed_dir`. The likely path is
that hooks load from a plugin directory rather than from `$CODEX_HOME/hooks.json`
directly. `codex plugin` is the surface to explore. Confirm any fix with a canary
hook that denies a unique string; there is no other way to observe it.

**The guard logic is NOT done. It is disabled.** An earlier version of this doc
said it was "done and tested (14 cases)". That was a smoke test, and the claim
was wrong. A skeptical review ran 53 cases and found 36 mismatches; an
independent 14-case re-check let 13 through, including `bash -lc "<rm>"`, which
is the form Codex actually shells out with, plus `git clean -fdx`,
`git checkout -- .`, `find -delete`, and `: > file`. It also fails open when
`python3` is unavailable, because the deny path pipes through it.

The cause is architectural. Regexes over raw shell text cannot gate a shell:
quoting, variable indirection, and interpreter nesting each defeat them, and
every patch widens the false-positive surface (`npm rm` and `docker rm` were both
denied). See `~/.claude/assets/reports/20260814-2145-skeptical-review/review.md`.

**What actually enforces, in priority order:**

1. **The sandbox.** `--sandbox read-only` for analysis, `workspace-write` for
   edits, never `--dangerously-bypass-approvals-and-sandbox`. OS-enforced rather
   than text-matched, so none of the bypasses above apply to it.
2. **The prose.** Preamble imperatives. In the one live test they held: told to
   `rm` a file, Codex refused, moved it aside, and reported where.
3. **Not giving Codex a path to what you cannot undo.** It has no push
   credentials it needs, and the repos are human-gated by policy.

A hook is worth revisiting only via `permission_request`, which gates by parsed
tool intent rather than by string matching.

### The output contract, which the schema gets wrong

The embedded JSON schema advertises `permissionDecision: allow|deny|ask`. The
runtime rejects two of those. The binary carries the error strings
`PreToolUse hook returned unsupported permissionDecision:allow`, the same for
`:ask`, and `PreToolUse hook returned permissionDecision:deny without a
non-empty permissionDecisionReason`. So: **deny is the only accepted decision,
it must carry a reason, and a passing hook emits nothing at all.** A hook written
against the advertised enum fails on its happy path.

## The IPC doorbell: required, and it needs two things

Earlier revisions of this doc called the doorbell optional and said it needed no
registered identity. Both were wrong, and the second was wrong in a way that
made every send fail.

**It needs two things, and they fail differently.**

1. **Sometimes network access.** The broker listens on a unix socket at
   `~/.claude-ipc/run/ipc.sock`, outside the workspace. Symptom when blocked:
   `error: Failed to connect`. Adding `--add-dir` on that directory does not
   help, which points at a `network-outbound` seatbelt rule rather than a file
   permission. The reliable fix on the launching side:

   ```
   codex exec --sandbox workspace-write -c sandbox_workspace_write.network_access=true
   ```

   **But this is not consistently required.** On 2026-08-15 a plain
   `--sandbox workspace-write` run sent successfully with no network flag, after
   two earlier runs on the same day failed to connect under what looked like the
   same conditions. The variable was not identified. Treat the send as
   best-effort: it may work without the flag, and the flag makes it reliable.
   Never let a run depend on it having succeeded.

2. **A registered sender.** The broker runs strict mode and rejects a send whose
   sender it cannot identify. `--from <name>` alone is NOT enough, despite the
   error text suggesting it: `not_registered: codex must register before sending
   (strict mode)`. Codex must run `claude-ipc register codex` first, every run,
   because the alias is session-bound and pruned on idle.

## Why the doorbell earns its cost, against the earlier ruling

This doc previously argued against registering Codex, on the grounds that a
write-only participant creates a mailbox nobody reads, and this project already
carries seven orphaned mailboxes. That reasoning weighed the wrong cost.

On 2026-08-14 Codex fixed a real bug (the credit-cycle anniversary drift) in a
sibling worktree. Its announcement failed on the `not_registered` error above, so
the Claude session tracking that work never learned who did it, and **attributed
Codex's fix to the owner in writing**. The owner had to correct it.

That is the cost of no attribution, and it is larger than an orphaned mailbox.
Codex runs with no WAL, no atone, no hooks, and no checkpoint. Its work is
precisely the work that most needs to be identifiable as not-Claude's and
not-the-owner's, because nothing else in the system records it. The mailbox is
the only cross-session identity channel; the handback file lives in one working
directory and says nothing to a session that never opens it.

So: register, send, and name the files touched in the message. An orphaned
`codex` mailbox is an acceptable price for knowing which agent changed what.

## What this is not

Not a peer session. A Codex run has no WAL, no checkpoint index, no IPC identity,
and no sub-agents. It sends one project-mailbox message when it finishes and
writes one handback file. Treat it as a contractor: brief it, read what it hands
back, decide what to keep.
